Why I Built This: Turning Lessons Into Engineering Guardrails 🛠️

👋 A warm welcome from Kunal • Hands-on Observations • Real Experiments
👨‍💻

Hey everyone! Welcome to the very first post on Buildlog by Kunal. The purpose of this space is straightforward: Learn it. Build it. Document it. As developers, we constantly experiment with new tools, break things, attend community talks, and figure out what actually works in production. Today, I'm documenting what I learned about running autonomous AI agents safely and sustainably.

A

What I Learned

Over the past few months of working with autonomous AI coding agents (including hands-on tests with the Gemini CLI and community sessions around container systems), I observed two critical realities:

01. SECURITY & TOKENS

Agents Are Curious Tourists

When you run an autonomous coding agent directly on your laptop, you tell it to fix one bug. Instead, it reads through every folder, indexes unrelated microservices, checks your environment variables, and burns through thousands of context tokens on files it was never meant to touch.

02. RESOURCE OVERHEAD

Unbounded Compute Burns Silicon & Energy

When agents loop endlessly on a failing test suite or load full-precision models independently into memory, CPU and GPU temperatures spike, battery drains, and cloud costs escalate. True AI sustainability isn't just about prompt compression—it's about hardware and execution discipline.

B

What Does "Green Sandboxes" Mean?

A Green Sandbox combines two essential engineering pillars:

Pillar 1: Sandboxing (Security)

Strict Isolation & Least Privilege

Restricting what the agent can see and do using lightweight virtual machines, folder-scoped mounts, filtered network egress, and secret placeholder masking. Prompts suggest boundaries; sandboxes physically enforce them.

Pillar 2: Green Computing (Sustainability)

Efficient Hardware & Ephemeral Lifecycles

Leveraging Docker Model Runner, model sharing across applications, 4-bit/8-bit quantization, and automatic idle-unloading so computing resources spin up on demand and shut down immediately when the job is done.

C

A Practical Example: The Tale of Two Runs

Imagine you have a project with 10 microservices and you assign an agent to resolve a bug in Microservice 1:

WITHOUT GREEN SANDBOX

The Wild Run on Your Laptop

  • Agent traverses Microservice 2..10, ingesting thousands of irrelevant lines into context.
  • Accidentally reads your local ~/.ssh or .env tokens.
  • Loops 15 times attempting a broken build, pegging your laptop CPU at 100%.
  • Spends your token budget on an unsolicited tour of your entire filesystem.
WITH DOCKER GREEN SANDBOX

The Engineered Enclave

  • Agent is mounted strictly to ./services/microservice-1. Other services do not exist.
  • Secrets are masked via placeholders; true API keys never enter the LLM's prompt context.
  • CPU is capped at 2 cores, RAM at 4GB, with hard iteration limits to halt runaway loops.
  • Tears down immediately upon task completion. Zero waste. Zero leaks.

Let's dive into the complete breakdown across three in-depth sections: from the original local-vs-sandbox experiment, to Docker Model Runner's environmental impact, to the technical implementation of Docker Sandboxes.

PART 01 • AGENT BOUNDARIES

Sandboxing AI Agents: Stop Giving Your Agent the Keys to the Entire House! 🔐🤖

⏱️ 5 min read • Architecture & Cost Containment • Gemini CLI Experiment
🧐

Imagine hiring a developer to fix one bug in your application, but instead of fixing it, they explore every folder, browse random websites, and keep trying the same solution for hours. Meanwhile, your computer is working hard, your tokens are disappearing, and your bill is getting ready to surprise you! 😂

That is one of the primary challenges we face when working with autonomous AI coding agents.
1.1

The Experiment: Local Machine vs. Sandbox

The main goal was to compare token usage and compute wastage when running an AI coding agent directly on a laptop versus inside a sandbox.

I took an issue from a large open-source project and attempted to solve it in both environments using Gemini CLI.

Standardized Test Setup

To make the comparison fair, I kept the model, prompt, context, and task the same.

I collected measurements such as:

📊

Input and Output Token Usage

Tracking exponential context expansion as agents ingest unrelated project files.

⏱️

Execution Time

Comparing runaway exploratory iterations against bounded task completion.

🔥

Peak CPU Usage

Measuring host hardware strain caused by unconstrained multi-process executions.

📦

Other Resource-Consumption Metrics

Evaluating memory residency, disk writes, and network bandwidth overhead.

The Core Question:

"Can we reduce unnecessary token usage and resource consumption by restricting what the agent can access?"

1.2

Why Do We Need Sandboxing?

An AI agent might be asked to fix a bug in one microservice, but it could explore unrelated files or other parts of the project.

🏛️

Imagine an application with 10 microservices. You ask the agent to fix a bug in Microservice 1, but it starts exploring Microservices 2 through 10 as well.

Congratulations! You asked for one bug fix and got an unsolicited architecture tour. 😂

With sandboxing, we can give the agent access only to the specific folder it needs.

This can reduce irrelevant exploration and potentially lower token consumption.

1.3

What Can We Control Inside a Sandbox?

Inside a sandbox, engineering mechanisms give us granular control over execution boundaries:

⚙️

CPU and memory limits

Give the agent a defined amount of computing resources instead of letting it consume everything available.

📂

File-system permissions

Decide which files the agent can read, modify, or access at all.

🛑

Process limits

Prevent the agent from endlessly retrying a failed solution. For example, if an agent repeatedly fails to fix a bug, we can impose execution limits rather than allowing it to continue indefinitely.

🌐

Network restrictions

Agents often like exploring the internet. We can restrict their access to approved websites and services.

⏳

Ephemeral execution

Start the sandbox when a task arrives and tear it down when the task finishes.

Why keep computing resources running all day if the task needs only a few minutes? Let the agent work, finish the job, and leave. No unnecessary overtime! 😂

1.4

Sandbox vs. Virtual Machine vs. Docker

A sandbox is not necessarily a virtual machine:

  • Docker containers generally share the host operating system's kernel.
  • Virtual machines run their own guest operating system and kernel.
  • Sandboxes provide controlled execution environments and can use containers, microVMs, full VMs, or cloud-based infrastructure.
Environment Kernel Sharing Isolation Level Startup Speed Primary Fit
Docker Containers Shares host OS kernel Process isolation (Namespaces & Cgroups) Milliseconds Consistent application packaging
Virtual Machines Independent guest OS & kernel Hardware virtualization Seconds to minutes Full multi-tenant server workloads
Sandboxes Lightweight VM / MicroVM / Enclave Controlled, isolated boundary with proxy policy Sub-second to fast Untrusted autonomous AI agent tasks

The goal is to choose the right level of isolation without wasting unnecessary computing resources.

1.5

What About Multiple AI Agents?

Suppose Agent A fixes a bug and Agent B needs its output.

Should Agent B get access to Agent A's entire environment? Not necessarily.

The agent harness or orchestration layer can collect Agent A's output, validate it, and pass the required information to Agent B.

This allows agents to collaborate without automatically giving them unrestricted access to each other's environments.

ORCHESTRATION ARCHITECTURE

Diagram 2: Multi-Agent Isolation & Orchestration Harness

Harness layer collects and validates outputs without cross-contaminating enclaves.

Figure 2: The Agent Harness decouples execution environments. Agent B never gains unrestricted visibility into Agent A's host files or memory.
1.6

The Bigger Engineering Idea

Instead of dedicating one permanently running virtual machine to every agent, we can explore running multiple isolated workloads on shared infrastructure.

Depending on the security requirements, this could involve containers, microVMs, Kubernetes jobs, or cloud execution environments.

The objective is to balance security, performance, resource utilization, and cost.

CORE PHILOSOPHY

Final Takeaway

"Prompts suggest boundaries. Engineering enforces them."

Telling an AI agent not to access a sensitive file is not the same as technically preventing it from accessing that file.

Sandboxing helps us control what an agent can access, how much computing power it can consume, where it can connect, and when its execution should stop.

Because building smarter AI agents is great—but building agents that don't wander around your entire codebase like curious tourists is even better! 😂🔐
PART 02 • GREEN AI INFRASTRUCTURE

Summary: Docker Model Runner and Environmental Sustainability 🌱⚡

⏱️ 4 min read • Hardware Optimization • Community Talk Learnings

The talk focused on how Docker Model Runner can help run LLMs efficiently while reducing resource consumption, cost, and environmental impact.

01

1. Docker Model Runner vs. Docker containers

  • docker model run runs an LLM through Docker Model Runner.
  • docker model ps shows model-related information.
  • docker ps shows running containers, but a model running in Docker Desktop does not necessarily appear as a separate container.
  • On Linux, models may run in containers, depending on the Docker Model Runner configuration.
02

2. Share models across applications

Multiple applications can use a shared model instead of loading separate copies, improving resource utilization.

03

3. Quantization reduces resource requirements

  • Full-precision, 8-bit, and 4-bit models differ in memory requirements and numerical precision.
  • Smaller quantized models generally require less memory and storage and can be faster or more energy-efficient.
  • However, quantization can reduce accuracy, depending on the model and task. Good prompting and choosing the right model are essential.
04

4. Improve GPU utilization

Underutilized GPUs waste resources. Better utilization can reduce the need for additional hardware and the associated manufacturing emissions.

05

5. Unload models when not in use

Unloading idle models frees memory and other resources, potentially reducing operating costs and energy consumption.

EFFICIENCY ARCHITECTURE

Multiple client applications sharing a single quantized model runner with auto-unload.

Figure 3: Docker Model Runner consolidates client applications onto a single quantized model with automatic idle-unloading.
2.4

Three Practical Ways to Improve AI Sustainability

01

Choose the right model

Match model size and capability to the task.

02

Measure resource usage

Monitor GPU utilization, energy consumption, and carbon emissions where possible.

03

Unload idle models

Free up memory when models are no longer needed.

PART 03 • IN-DEPTH IMPLEMENTATION

Docker Sandboxes: A Safer Way to Run AI Agents 🛡️🐳

⏱️ 7 min read • Zero-Trust AI Engineering • Lightweight Virtual Machine Isolation

We all know Docker for containers. But with the rise of AI agents, there's a new challenge: how do we let AI work autonomously without giving it access to everything on our system?

That's where Docker Sandboxes come in.

The Challenge of Autonomous Execution:

AI agents can read files, execute terminal commands, access APIs, install dependencies, and even build and run applications. These capabilities make them powerful, but they also introduce security risks. An agent with excessive permissions could expose API keys, modify important files, or make unauthorized network requests.

Instead of relying entirely on the agent to behave correctly, sandboxing lets us define boundaries around what it can do.

3.1

What exactly is a Docker Sandbox?

A container packages an application and its dependencies into an isolated environment. A sandbox takes the idea of isolation further by providing controls over an agent's access to files, networks, and sensitive resources.

Docker Sandboxes use lightweight virtual machines to isolate agent workloads. This helps separate the agent's execution environment from the host system and other workloads.

🎯
The idea is simple: let the agent do its job, but limit the damage it can cause if something goes wrong.
3.2

Four important security controls

1

1. File system access

An AI coding agent may need access to your project folder, but it doesn't necessarily need access to your entire computer.

With controlled file system access, you decide which folders the sandbox can use. This reduces the risk of an agent reading private documents, SSH keys, or unrelated project files.

2

2. Network access

Even if an agent is isolated, it may still attempt to connect to external websites or APIs.

Docker Sandboxes allow network access to be controlled through policies. For example, you could allow access to a required API while blocking connections to other domains.

This is particularly useful when an agent processes untrusted code or encounters malicious instructions hidden inside a file or webpage.
The principle is to deny access by default and allow only what the task requires.
3

3. Secret management

This is one of the most important parts of agent security.

API tokens and credentials can provide access to repositories, cloud services, databases, and paid APIs. If a secret is exposed, someone else might misuse it, access private resources, or generate unexpected costs.

Docker Sandbox secret handling can keep the actual secret outside the agent's visible context. In supported configurations, the agent uses a placeholder that is replaced with the real credential when an authorized network request leaves the sandbox.

The agent can make the required request without needing to know the actual token value.

However, this doesn't remove every risk. If an agent is authorized to use a credential, it may still misuse that access. That's why least-privilege credentials and strict network policies remain essential.
4

4. MCP and tool access

Model Context Protocol (MCP) allows AI applications to connect with external tools and services.

But connecting an agent to more tools also expands what it can potentially do. An agent connected to a GitHub MCP server, for example, might be able to inspect repositories or perform other actions depending on its permissions.

The solution is to configure only the tools and capabilities required for the task, rather than giving the agent unrestricted access to every available integration.

3.3

A practical example: Let an AI agent build an application

Imagine asking an AI coding agent to build a Python application, test it, and push the code to GitHub.

Without proper boundaries, the agent might have access to unrelated files, credentials, and network destinations.

With a sandbox, the workflow can look like this:

1

1. Create a sandbox for the coding agent.

Provision an ephemeral, isolated lightweight VM container.

2

2. Give it access to the required project directory.

Mount strictly the target folder, preventing access to unrelated workspace directories.

3

3. Allow only the network destinations needed for development.

Configure egress rules for packages and APIs; block arbitrary internet access.

4

4. Configure the GitHub credential securely.

Use opaque placeholders so raw secrets never enter prompt context.

5

5. Let the agent write code, build a Docker image, and run tests inside its environment.

Autonomous task execution operates with full compiler/testing tools safely inside.

6

6. Review the results before allowing sensitive or irreversible actions.

Human-in-the-loop review ensures safe commits and releases.

The agent can complete much of the work autonomously without receiving unrestricted access to the host system.
3.4

Can we run Docker inside a Docker Sandbox?

Yes, supported Docker Sandbox workflows can allow agents to build and run containers inside their sandbox.

CONTAINERIZED RUNTIME

For example, an agent can create a Python script, write a Dockerfile, build an image, run a container, and check the output.

This makes the sandbox useful not only for writing code but also for testing and executing the applications the agent creates.

The important detail is that sandbox permissions still matter. Access to Docker services, image registries, and external networks should be configured according to the task's requirements.
3.5

What about YOLO mode?

Developers increasingly use AI coding tools in autonomous modes, often called YOLO mode, where the agent can execute commands with fewer approval prompts.

This saves time, but repeatedly approving commands isn't the only way to stay safe.

A better approach is to establish security boundaries before the agent starts working. Restrict its file system access, control network connections, manage secrets securely, and limit its available tools.

That way, autonomy doesn't have to mean unrestricted access.
Of course, sandboxing isn't a guarantee against every attack. Misconfigured permissions, authorized but dangerous actions, and vulnerabilities still need to be considered.
3.6

Containers vs. sandboxes

The two concepts serve related but different purposes.

Containers

Package and run applications consistently.

Sandboxes

Provide an environment for restricting and isolating potentially risky workloads.

Docker Sandboxes

Combine isolated execution with controls designed for AI coding agents and other development workflows.

They aren't competing technologies. Containers remain important, while sandboxing addresses additional security challenges that arise when agents can execute commands and interact with external systems.

✨

Final thoughts

AI agents are moving beyond answering questions. They can now write code, execute commands, interact with APIs, and complete multi-step tasks with minimal human intervention.

That makes security a design requirement, not something to think about after deployment.

Docker Sandboxes offer a practical approach: define the boundaries, provide only the permissions required, and let the agent work within them.

"The goal isn't to stop AI agents from working. It's to give them the freedom to work without giving them the keys to everything." 🔐🚀
